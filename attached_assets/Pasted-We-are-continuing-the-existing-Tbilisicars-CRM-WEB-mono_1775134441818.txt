CHANGE 1 — Upgrade booking Assign flow inside booking details
==================================================

Current known behavior:
- In booking details, near the vehicle/model area, there is an Assign action
- It opens a modal and allows assigning an available vehicle
- This works, but is too limited for real operations

Required behavior:
1. Inside the same Assign flow/modal, staff must be able to:
   - assign a specific available vehicle
   - unassign/remove the currently assigned vehicle
   - change the booking’s selected vehicle model
   - indirectly change brand by selecting a model from another brand

2. Real use case to support:
   - booking may be planned with one model in advance
   - at pickup time customer may request another car
   - staff must be able to switch model and/or vehicle quickly from this same Assign flow
   - staff should NOT be forced into full Edit Booking just to change model/vehicle assignment

3. UX rules:
   - show current selected model clearly
   - show current assigned vehicle clearly (if any)
   - allow selecting another model
   - once model changes, refresh available vehicles for that model
   - provide a clear “Unassign vehicle” action if a vehicle is currently attached
   - keep flow simple and operational, not overly complex

4. Data rules:
   - if vehicle changes, update booking.vehicleId
   - if model changes, update booking.vehicleModelId
   - if vehicle is unassigned, vehicleId becomes null
   - booking must remain valid even if vehicleId is null
   - do not break existing booking detail rendering

5. API/backend rules:
   - first audit whether existing booking update endpoint/service already supports vehicleModelId + vehicleId updates
   - if yes, reuse it
   - only add minimal API support if current route truly cannot support this
   - do not create redundant endpoints if existing booking patch/update flow can handle it safely
