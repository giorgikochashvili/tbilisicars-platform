1) VEHICLE CITY VISIBILITY / LOCATION INTEGRITY
- A vehicle must not appear in all cities.

- If a vehicle is currently based in Kutaisi, it must not appear anywhere in Tbilisi or Batumi.
- If a vehicle is currently based in Batumi, it must not appear anywhere in Tbilisi or Kutaisi.
- This rule must hold consistently in:
  - booking creation
  - booking edit / assign vehicle
  - timeline
  - calendar
  - operational boards
  - any vehicle selection dropdowns
  - any fleet availability logic

2) VEHICLE CREATION DEFAULT LOCATION BEHAVIOR
- When creating a vehicle, there are 3 main regions/cities:
  - Tbilisi
  - Kutaisi
  - Batumi
- For those main city choices, the default sub-location should be the airport location for that city.
- Analyze how vehicle current location is currently stored and how the city/location relationship works in the existing schema and UI.

3) WHEN VEHICLE LOCATION SHOULD CHANGE
- Vehicle location should NOT randomly change just because of booking assignment.
- Vehicle location should only be changed by actual operational workflow.
- The important operational cases:
  A. If a vehicle is rented in one city and actually goes out on that rental, after pickup it must operationally belong to the route outcome described by the booking flow.
  B. If that rental is cross-city, the vehicle must be reflected in the correct city for operations, calendar, and next availability handling.
  C. If vehicle returns in Downtown or another actual dropoff location, vehicle current location should be updated on the vehicle record accordingly after the correct operational event.

4) HARD VEHICLE LOCK AFTER PICKUP
- Once a specific vehicle is picked up on a booking, that vehicle must not be assignable to another booking until its active booking reaches its dropoff end and operational completion.
- Example:
  - vehicle XX123XX
  - pickup: 15.04 15:00
  - dropoff: 18.04 18:00
  - once pickup is completed, XX123XX must not be assignable elsewhere before that booking is finished
- This must be enforced in backend availability logic, not just UI hiding.

5) SOFT “RETURNING SOON” WINDOW FOR ASSIGN
- Desired enhancement:
  - if a vehicle is returning very soon, it may appear in assign dropdown in a warning state
  - target window: 2 hours before its scheduled return
- Example:
  - vehicle returns at 18:00
  - if another booking pickup is at 15:30 -> vehicle should NOT appear
  - if another booking pickup is at 16:00 or later -> vehicle may appear in assign list
- In this “returning soon” case:
  - vehicle should be visually differentiated in assign dropdown with a light blue / cyan style or equivalent clear warning state
  - assignment may be allowed
  - BUT pickup for the next booking must still be blocked until the previous booking has actually completed dropoff
- This means:
  - soft availability for assignment
  - hard block for pickup until prior rental is operationally closed

6) PICKUP MUST NEVER BE POSSIBLE IF PRIOR RENTAL NOT CLOSED
- No matter what is assigned visually, a staff member must not be able to complete pickup on a booking if that vehicle still has any active unfinished prior rental.
- This rule must be enforced in backend operational action validation, not only in UI.
