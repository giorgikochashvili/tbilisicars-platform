Correction 1 — C1 transaction-only fix may not fully prevent the race

You wrote that SELECT ... FOR UPDATE is not advisable now and that moving the conflict check inside the transaction is sufficient.

Please re-check this carefully.

In PostgreSQL default READ COMMITTED isolation, two concurrent transactions can both:
1. start a transaction,
2. check overlapping bookings and see no conflict,
3. insert/update overlapping bookings,
4. both commit.

So simply moving checkVehicleConflict inside db.transaction may still not fully prevent the race unless there is a lock or DB-level exclusion constraint.

We do not want a DB migration/exclusion constraint in this batch.

- inside the transaction,

- then run validateVehicleBelongsToModel if needed,
- then run checkVehicleConflict using the same tx,
- then insert/update the booking.

Concurrent admin requests for the same specific vehicle must serialize on the vehicle row lock. The second request should wait until the first commits, then re-check conflicts and return the existing ConflictError/409 if overlap exists.
