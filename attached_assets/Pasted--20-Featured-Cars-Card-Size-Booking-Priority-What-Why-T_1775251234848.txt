#20 - Featured Cars Card Size + Booking Priority
What & Why
Two small, tightly-scoped UI fixes for the Featured Cars feature:

The homepage Featured Cars card images are still object-cover which crops wide side-view car PNGs. Change to object-contain so the full car silhouette is visible. The card widths and image wrapper height from task #20 (w-[340px] sm:w-[400px], h-44) are already in the code but need to be confirmed present in the rendered JSX.

When a user arrives on the Booking page with a vehicleModelId in the URL (clicked from a Featured Car), the selected vehicle should appear first in the vehicle grid. Currently it can appear anywhere in the list. A minimal derived display array (selected first, rest in original order) fixes this with zero impact on availability or pricing logic.

Done looks like
Homepage Featured Cars: side-view car PNGs are fully visible (not cropped), filling the card naturally
Booking page: when opened from a Featured Car link, the clicked vehicle model appears as the first card in the vehicle grid and is highlighted/selected
If no vehicleModelId is in the URL, the booking page vehicle order is unchanged
If the vehicleModelId is not in the available results, the page works exactly as before
Out of scope
CRM Featured Cars module
Upload logic, DB schema, admin API, public Featured Cars API
Homepage hero or any other homepage section
Booking availability engine, pricing, insurance, payment logic
Any unrelated booking step or UI component
Tasks
Fix Featured Cars image fit — In Home.tsx, on the featured car image element, change object-cover to object-contain (keeping object-center, w-full, h-full, and overflow-hidden on the wrapper). Confirm the card also has w-[340px] sm:w-[400px] and image wrapper has h-44 — if not, apply those too.

Sort selected vehicle first on Booking page — In Booking.tsx, immediately before the filteredModels.map() call in the vehicle grid (around line 764), derive a displayModels array that places the model matching form.vehicleModelId first, then maps over displayModels instead. No source data mutated; no business logic touched.
