Task: Fix public website pricing source to correctly follow Parent/Child WEB rate hierarchy

Project context:
Tbilisicars CRM&WEB monorepo (React + Express).
The public website (Fleet + Booking) must display prices coming strictly from CRM Rates (WEB).

Current problem:
Public endpoint /api/public/booking-config returns many models with min_price_per_day = 0,
even though valid prices are entered in CRM Rate Plans.

Frontend is already fixed and correctly shows:
- price when price !== null
- "Contact for pricing" when price === null

Therefore the issue is NOT frontend.
The issue is in how the public API calculates min_price_per_day.

Business requirements (STRICT):

1. Rates system logic:
- There are WEB rates only (ignore BROKER for now)
- There is a Parent rate (long-term base pricing)
- There are optional Child rates (date-specific overrides)
- Child rates inherit from Parent but can override specific models/prices

2. Correct pricing resolution rule:

For any model:

IF there is an active WEB Child rate covering the requested period:
    → use that Child rate

ELSE IF there is an active WEB Parent rate:
    → use Parent rate

ELSE:
    → price = null (show "Contact for pricing")

3. min_price_per_day must be:
- the lowest valid price_per_day from rate tiers of the selected rate
- NEVER default to 0
- NEVER fallback to 0 if no tier exists
- MUST be null if no valid rate tier exists

4. On Request (vehicle_count = 0):
- MUST NOT affect price
- pricing and availability are independent

CRITICAL RULES:
- DO NOT change database schema
- DO NOT change CRM UI or rate creation logic
- DO NOT touch accounting logic
- DO NOT redesign API structure
- DO NOT hardcode any price
- DO NOT introduce fallback hacks like "if 0 then 50"
- DO NOT break existing booking flow
- Only fix pricing resolution logic inside public API

Investigation steps:

1. Inspect:
artifacts/api-server/src/routes/public-bookings.ts

2. Find how min_price_per_day is currently calculated
- likely a lateral join or aggregation over ratetier

3. Identify why:
- many models return 0 instead of real prices
- incorrect joins OR wrong rate selection OR missing filtering

4. Fix logic so that:

For each vehicle_model:
- select correct active WEB rate (Child first, then Parent)
- join ONLY that rate's tiers
- compute MIN(price_per_day) WHERE price_per_day > 0
- if no tiers → return NULL

Important:
price_per_day = 0 must be treated as INVALID (ignore it)

Expected SQL behavior (conceptual, not exact code):

SELECT MIN(rt.price_per_day)
FROM ratetier rt
WHERE rt.vehicle_model_id = vm.id
  AND rt.price_per_day > 0
  AND rt.rate_id = selected_rate_id

Where selected_rate_id is determined by:
- active Child rate for date
- else Parent rate

Expected result after fix:

- All models that have valid CRM WEB rates show correct min_price_per_day
- No model returns 0
- Models without rates return null
- Website correctly displays price for all priced models
- "Contact for pricing" only appears when truly no rate exists
