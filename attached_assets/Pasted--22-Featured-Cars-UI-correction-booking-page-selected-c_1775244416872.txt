#22 - Featured Cars UI correction + booking page selected-car priority
What & Why
Two tightly-scoped improvements are needed for the new Homepage Featured Cars feature.

Issue 1 — Homepage Featured Cars card proportions still did not visibly change
The previous UI adjustment did not produce a visible improvement. The cards are still too narrow for side-view vehicle images, and the image still dominates the card visually.

Issue 2 — Clicking Featured Cars "Book Now" should surface that exact selected vehicle first on the booking page
When a user clicks a Featured Cars card/CTA and lands in the booking flow, the selected vehicle model must be visually prioritized in the vehicle selection step. The exact clicked model should appear first in the vehicle list/cards when the booking page loads with the preselected vehicleModelId in the URL.

This must be done safely:
- no booking logic rewrite
- no availability logic changes
- no pricing logic changes
- no CRM/data model changes unless absolutely unnecessary
- no broad refactors

Important constraints
- The project is already fully built and integrated. Do not damage existing behavior.
- Do not make speculative changes.
- Reuse the current route/query-param behavior that already exists for featured cars.
- Only improve the exact UI/UX requested.
- Keep changes minimal, production-safe, and tightly scoped.

Goals
1) Make Homepage Featured Cars cards visibly wider and more balanced for side-view car images.
2) Ensure that when a featured car is clicked, that same selected model is surfaced first in the booking vehicle-selection view when the booking page opens.

PART B — Booking page should prioritize the clicked featured car
==================================================

Business intent
When a user clicks a Featured Cars card or its CTA, the homepage already navigates into the booking flow with a preselected vehicleModelId in the URL. That existing mechanism must remain unchanged.

Now improve the booking-page UX so that:
- the selected vehicle model from vehicleModelId is shown first in the vehicle cards/list
- the selected vehicle remains clearly highlighted/selected using the current project’s selection styling
- if the selected/preferred model is unavailable for the currently chosen search criteria, the booking flow must continue gracefully using existing logic without breaking

Required files to inspect first
- artifacts/website/src/pages/Booking.tsx
- the exact section where available vehicle cards/models are built/rendered
- the existing code that reads vehicleModelId from the URL
- any existing sort/filter/select logic for the vehicle cards

Required implementation
1. Keep the existing URL-based preselection behavior intact.
2. In the vehicle selection step, when vehicleModelId is present and matches one of the currently rendered available vehicle models/cards:
   - reorder the rendered list so the matching selected model appears first
   - preserve all remaining items in their existing relative order after that
3. Keep the existing selected/highlighted state for the matched model/card.
4. Do not alter business logic for:
   - search
   - availability
   - pricing
   - insurance
   - payment
5. If vehicleModelId is present but the matching model is not available in the current results:
   - do not break the page
   - do not inject fake data
   - do not force selection
   - simply continue with the normal existing result list/behavior

Implementation rule
Do not rewrite the booking engine.
Only apply a minimal, view-layer ordering adjustment at the point where the available vehicles/models are prepared for rendering.

Preferred logic
If there is currently an array of available models/cards being rendered, derive a display array like:
- selected match first
- all other items after it in original order

Do not mutate source data in risky ways if an immutable derived array is safer.
