# Task — WEB Rates Refactor: Parent/Child Pricing Structure + WEB/BROKER Split

You are working inside an already built and operational Tbilisicars CRM + Website monorepo. This system was already created in Replit and contains working pricing, booking, promotions, fleet, and CRM logic. Your job is NOT to rebuild or redesign the system. Your job is to carefully UPGRADE and RESTRUCTURE the Rates module for WEB pricing only, without breaking anything that already works.

CRITICAL RULES:
- Do NOT refactor unrelated code.
- Do NOT break existing booking flow, fleet logic, dashboard logic, or manual CRM booking logic.
- Do NOT redesign the whole Rates page from scratch if the current structure can be extended safely.
- Reuse existing DB tables, services, routes, and UI components wherever possible.
- All changes must be incremental, minimal, and safe.
- If something already exists, EXTEND it — do not replace it blindly.
- Keep backend as the single source of truth for pricing resolution.
- Do NOT introduce speculative architecture.
- This task is ONLY about WEB pricing architecture. BROKER must be visually separated, but BROKER pricing logic itself should not be rebuilt in this task.

---

## OBJECTIVE

Restructure the Rates module so that Rates are clearly split into:

1. WEB
2. BROKER

For this task, implement WEB pricing architecture only.

WEB pricing must become a hierarchical system with:

- Parent Rate (main/base rate)
- Child Rate (derived/seasonal rate under a parent)

Pricing must remain MODEL-BASED, not category-based.

Promotions must remain a separate layer:
- Promotions must select from already created WEB rates
- Promotions then apply discount or price increase on top of the resolved WEB price
- Promotions must not rewrite stored base rates

One Way Fee, grace period, minimum 2-day rule, and quote/booking pricing logic already implemented previously must remain intact and must continue to work correctly with the new Parent/Child rate architecture.

## BUSINESS LOGIC TO IMPLEMENT

### 1. Split Rates into WEB and BROKER
In the Rates UI, separate rate plans into:
- WEB
- BROKER

This can be tabs, segmented controls, or another clean existing-style switch.

For this task:
- fully implement WEB structure
- do not break existing BROKER area
- do not redesign or rebuild BROKER pricing logic yet

---

### 2. WEB Rates must be model-based
WEB prices must be written for VEHICLE MODELS, not categories.

Each WEB rate must support:
- name
- valid date range
- locations / regions where it applies
- selected models
- day ranges
- prices per model per day range

This is the core source price for website bookings.

---

### 3. Parent Rate
A Parent Rate is the main/base WEB rate.

It is created once and acts as the source/base pricing structure.

It contains:
- name
- active date period
- locations / regions
- selected models
- day ranges
- model price matrix

This is the base WEB price.

---

### 4. Child Rate
A Child Rate is a sub-rate under a Parent Rate.

A Child Rate:
- MUST reference a Parent Rate
- has its own valid date range
- is created by selecting a Parent Rate
- MUST preload the Parent Rate’s full current pricing dataset into an editable child form
- after loading parent data, user can edit prices freely
- when saved, Child Rate stores FULL values, not partial diffs

IMPORTANT:
Do NOT implement runtime inheritance/diff resolution.
Do NOT build a fragile partial override system.
A Child Rate must behave as:
- full editable copy initialized from Parent
- then saved as its own full pricing dataset with parent reference

This is intentional for stability and to avoid bugs.

---

### 5. Promotions must remain a separate layer
Promotions are NOT the same as WEB rates.

Do not merge Promotions into Rates.

Promotions must work like this:
- admin selects an already created WEB rate context
- then applies:
  - discount
  - or price increase

Promotions must only affect final calculated price.
Promotions must not overwrite stored Parent/Child rate values.

Pricing order must remain:

1. Resolve correct WEB rate
2. Apply pricing from Parent/Child rate
3. Apply grace period + min 2 days logic
4. Apply One Way Fee separately
5. Apply Promotion only to rental price portion
6. One Way Fee must remain fixed and untouched by promotion

---

### 6. No overlapping WEB rates
WEB rates must not overlap in conflicting date ranges.

Reject create/update if overlap is detected for conflicting WEB rates.

Do not allow multiple conflicting active WEB prices for the same operational context.

Implement safe validation so the system does not become ambiguous.
