Task: Implement true multi-assignee support in Tasks module using the existing task_assignees table

Context:
This is a live production-connected monorepo fully built in Replit. We are in a careful stabilization/build phase and must avoid breaking existing operations.

Important clarification:
The business requirement is that one task must be assignable to multiple staff members at once.
Example: a task may be assigned to 1, 2, 3, or more employees simultaneously.
So the current single-assignee-only behavior is not sufficient.

The previous audit already confirmed:
- tasks currently behave as single-assignee only
- task_assignees table already exists in the DB schema
- task_assignees is currently unused dead code
- visibility/scoping today is based only on tasks.assignedToId

CRITICAL RULES:
- Do NOT refactor architecture broadly
- Do NOT redesign the Tasks module UI unnecessarily
- Reuse the existing task_assignees table
- Keep existing task behavior stable for admin/full-access users
- Implement this carefully and minimally, without breaking task lists, counters, comments, or activity logs

Goal:
Add real multi-assignee support end-to-end so a task can be assigned to multiple staff members and correctly appear for all of them.

Requirements:

1. Data model / source of truth
- Analyze how to safely introduce multi-assignee behavior using task_assignees as the operative assignment source
- Decide how tasks.assignedToId should behave during transition:
  - keep for backward compatibility / primary assignee if needed
  - but do NOT leave visibility logic dependent only on assignedToId
- Propose the safest minimal migration strategy

2. Backend create/update
- Task create flow must support selecting multiple assignees
- Task update flow must support changing the full assignee set
- Writes to task_assignees must stay in sync and not leave stale rows

3. Backend visibility/scoping
- Non-fullAccess users must see tasks where they are one of the assignees
- Admin/full-access users still see all tasks
- GET /admin/tasks
- GET /admin/tasks/:id
- comments/activity access checks
- /admin/tasks/my-summary
must all follow the new assignment logic consistently

4. Frontend create/edit UI
- Replace the single "Assignee" select with a minimal multi-select / multi-assignee picker
- Reuse existing admin/team data and existing design patterns if possible
- Keep it simple and operational, not fancy

5. Frontend display
- Tasks list and task details should clearly show multiple assignees
- Existing filters/counters should remain understandable
- "My Tasks" should include any task assigned to the logged-in user, even if there are other assignees too

6. Safety
- Comments, activity log, and permissions must not break
- Existing tasks with only assignedToId and no task_assignees rows must still remain visible/usable
- Propose any backfill or compatibility handling if needed

Output format:
A. Exact backend files/functions to change
B. Exact frontend files/components to change
C. Safest assignment model strategy
D. Minimal implementation plan step by step
E. Risks/compatibility concerns to watch carefully
