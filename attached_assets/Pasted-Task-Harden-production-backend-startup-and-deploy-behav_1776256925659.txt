Task: Harden production backend startup and deploy behavior after recent live outage

Context:
This is a live production-connected monorepo (Tbilisicars CRM & WEB), currently operating on Batumicars.com as the temporary domain.
Recent Replit code changes + subsequent droplet deploy caused a production outage:
- CRM became inaccessible
- website lost operational API-backed data such as location lists
- API process appeared "online" in PM2 but did not actually listen on port 5000

We manually recovered the server by exporting env vars on the droplet:
- PORT=5000
- DATABASE_URL=postgres://tbilisicars:tbilisicars123@localhost:5432/tbilisicars
- RESEND_API_KEY=dummy

Confirmed findings from live logs:
- backend now requires PORT at startup and crashes if PORT is missing
- DATABASE_URL was also required and missing from PM2 runtime env during deploy
- this was enough to break CRM + public website operational endpoints
- we do NOT want this kind of fragile deploy behavior again

CRITICAL RULES:
- Do NOT refactor architecture
- Do NOT redesign deployment stack
- Do NOT change business logic
- Do NOT touch unrelated CRM or website features
- Focus only on startup/deploy robustness for production
- Keep fixes minimal, surgical, and low-risk

Goal:
Make production startup reliable so a normal deploy does NOT break the API just because PM2 runtime env is incomplete.

Audit and plan scope:
1. Inspect current backend startup requirements
- Identify exactly where PORT is now enforced
- Identify exactly where DATABASE_URL is enforced
- Identify whether startup behavior changed recently in a way that broke previous deploy assumptions

2. Inspect safest minimal production fix
We need the safest minimal production behavior for this droplet environment:
- API must default safely to PORT=5000 if PORT is missing
- DATABASE_URL handling must remain strict enough for correctness, but deploy behavior must be clear and stable
- RESEND_API_KEY must NOT take down the whole API in this current phase if email is not configured
- startup must not appear "online" while functionally dead

3. Decide the best surgical fix
Possible acceptable directions:
- add safe default for PORT (preferred if low-risk)
- ensure startup logging is explicit and production-friendly
- make email dependency non-fatal in this phase if that is safer
- preserve the existing business/application behavior otherwise

4. Deployment compatibility
- The fix must work with the current droplet + PM2 deploy style
- Do NOT require large infrastructure redesign
- Do NOT require Docker/systemd migration
- Do NOT require broad environment-management refactor

Output format:
A. Exact root cause(s) of the outage
B. Exact files/functions involved
C. Minimal permanent fix plan
D. What should remain strict vs what should become tolerant
E. Exact files that would be changed
F. What will NOT be changed
