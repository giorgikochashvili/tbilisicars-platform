# Task — Rates UX/Structure Correction: Parent Rate Defines Day Ranges, Rows Use Add Model (Not Add Tier)

You are working inside an already built and operational Tbilisicars CRM + Website monorepo. The Rates module was recently upgraded with WEB/BROKER split and Parent/Child logic, but the WEB Parent Rate creation flow and expanded row structure still do not match the intended business workflow.

This is NOT a rewrite. This is a precise correction of the newly built Rates UX and data-entry structure.

CRITICAL RULES:
- Do NOT rebuild the Rates module from scratch.
- Do NOT remove the existing WEB/BROKER split.
- Do NOT remove Parent/Child architecture.
- Do NOT break current quote, booking, one-way fee, promotion, grace-period, or min-2-days logic.
- Do NOT change unrelated CRM modules.
- Reuse the current Rates page and current backend structure as much as possible.
- Keep changes minimal, safe, and targeted.
- If existing tier storage can support this workflow, adapt it instead of inventing a new pricing system.

---

## OBJECTIVE

Correct the WEB Parent Rate workflow so it behaves like this:

1. When user clicks Add Rate Plan → Parent Rate,
   the Parent Rate creation modal must include:
   - Name
   - Description
   - Valid From
   - Valid Until
   - Minimum Days
   - Maximum Days
   - Active Status
   - Day Range definition section

2. The Day Range definition section must be part of the Parent Rate creation flow itself.
   Example default ranges:
   - 1–3
   - 4–7
   - 8–13
   - 14+

3. After Parent Rate is saved, expanding that rate must NOT show “Add Tier”.
   It must show “Add Model”.

4. Clicking Add Model must let admin choose a vehicle model, and then create/edit a row for that model using the day ranges already defined on the Parent Rate.

5. For each added model, the admin must be able to enter and later edit prices for each Parent-defined day range.

In short:
- Parent Rate defines the structure (date range + day ranges)
- Model rows hold the actual prices
- “Add Tier” wording/behavior is wrong for WEB pricing and must be corrected to model-oriented entry

---

## BUSINESS WORKFLOW TO IMPLEMENT

### 1. Parent Rate Creation Modal
The Parent Rate creation modal is currently too thin and only captures header fields.

It must be extended so that, during Parent Rate creation, the admin can also define the rental day ranges that this rate will use.

At minimum support the typical ranges:
- 1–3
- 4–7
- 8–13
- 14+

These ranges may already exist in current tier/min/max fields — inspect current structure and adapt carefully.

Important:
- Do NOT force a whole new schema if the current system already stores minDays/maxDays or similar tier boundaries
- Reuse the existing rate/tier structure if possible
- The modal should let the admin define the pricing grid structure before any model is added

---

### 2. Save Parent Rate = Save Pricing Structure
When the Parent Rate is saved, the system should save:
- the rate header
- the day-range structure for that rate

This means the Parent Rate becomes the container/structure for future model pricing rows.

Do NOT require model pricing during Parent creation.
Model pricing comes after, via Add Model.

---

### 3. Expanded Parent Rate Row
When a WEB Parent Rate row is expanded:

Current behavior:
- shows “Add Tier”

Required behavior:
- replace “Add Tier” with “Add Model”

Reason:
WEB pricing is model-based, and the current tier-first wording is confusing and wrong for the intended workflow.

---

### 4. Add Model Flow
When Add Model is clicked:

- user selects a vehicle model
- then the interface creates a pricing row/block for that model
- the columns for that row must match the Parent Rate’s defined day ranges
  for example:
  - 1–3
  - 4–7
  - 8–13
  - 14+

Then the admin can:
- enter prices manually
- save prices
- later edit prices

This should feel like:
Rate Plan → Add Model → Fill prices by day range

NOT:
Rate Plan → Add Tier generic

---

### 5. Existing Data Structure
You must inspect how the current system stores tiers and model pricing.

Preferred implementation:
- keep using the current tier storage if it already supports:
  - rate
  - vehicleModelId
  - minDays/maxDays
  - price

If so, simply reframe the UI and creation flow to match the intended model-based experience.

Do NOT invent a second pricing storage table unless absolutely necessary.

---

### 6. Child Rate behavior
Do NOT remove Child Rate logic.

But Child Rate must follow the same conceptual structure:
- it is still based on a Parent Rate
- it still preloads pricing data from the parent
- but the UI must remain model-oriented, not generic “tier” wording

If possible, adapt Child UI wording/structure so it stays consistent with:
- day ranges defined by the selected parent
- model rows containing prices

Do not over-refactor if Parent correction is the main required change.
