# RESERVATION CODE ARCHITECTURE

Add support for **two different booking reference values**:

## 1. externalReservationCode

This stores the code found on the imported broker/supplier voucher, if present.

Examples:

* DC-48291
* VIP-7741

## 2. reservationCode

This is the internal CRM-generated booking reference.

This internal code must be generated automatically from the **pickup location code prefix + next numeric sequence**.

Format:
`[PREFIX][NUMBER]`

Examples:

* TBI8001
* BAT8002
* KUT8003
* TBD8001
* TBH8001
* BATD8001
* BATH8001
* KTD8001
* KTH8001

---

# EXACT PREFIX MAPPING

Use **pickup location** to determine the internal reservation code prefix.

Use this exact mapping:

## Tbilisi

* **TBI** = Tbilisi Airport / Tbilisi International Airport
* **TBD** = Tbilisi Downtown
* **TBH** = Tbilisi Hotel

## Kutaisi

* **KUT** = Kutaisi Airport / Kutaisi International Airport
* **KTD** = Kutaisi Downtown
* **KTH** = Kutaisi Hotel

## Batumi

* **BAT** = Batumi Airport / Batumi International Airport
* **BATD** = Batumi Downtown
* **BATH** = Batumi Hotel

Do not derive prefixes from free text in a fragile way if the project already has normalized locations. Prefer mapping from the existing location entity / location type / location code structure. If needed, add a clean minimal mapping field or helper, but do not redesign the whole location system.

---

# SEQUENCE RULE

The numeric part must:

* start from **8001**
* be **prefix-specific**
* increment separately per prefix
* be safe against duplicates/race conditions

Examples:

* TBI8001, TBI8002, TBI8003
* BAT8001, BAT8002
* TBD8001, TBD8002
* KTH8001

Do not use one shared global sequence for all prefixes.

Implement this safely. If needed, create a small dedicated sequence table or equivalent safe mechanism. Keep it minimal and reliable.
