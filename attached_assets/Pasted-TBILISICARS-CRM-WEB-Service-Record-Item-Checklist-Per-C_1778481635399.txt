TBILISICARS CRM&WEB — Service Record Item Checklist / Per-Category Completion Plan

We need to improve the existing Service & Maintenance module, but first inspect and plan only. Do not implement yet.

Current behavior:
- Service records can have multiple Service Categories selected.
- These categories appear as red badges in the table.
- A service record has one shared Cost field and one shared Work Description / Notes field.
- The right-side three-dots action menu opens the existing Edit Service Record modal.
- The Edit modal currently allows editing vehicle, categories, date, status, mileage, cost, vendor/shop, mechanic, and notes.

New desired behavior:
Each selected Service Category inside a service record should behave like a checklist/work item.

Example:
If a service record has 3 categories selected:
- Tires
- Oil & Filter
- Lights

Then the expanded row detail should show all 3 items.
Pending/not completed items should appear in red.
Completed items should appear in green.
Staff should be able to mark individual items as completed while leaving others pending.

Business requirement:
- A service record may be overall Scheduled/In Progress/Completed.
- But inside it, each selected category/item should have its own completion state.
- If 3 things are planned and only 2 are completed, the 2 completed items should become green and the remaining item should stay red.
- The system should also support cost visibility:
  - ideally each item/category can have its own cost
  - expanded detail should show per-item cost if available
  - total cost should be visible
- Notes/description should remain editable.
- Existing Edit Service Record flow must not break.
- The right-side three-dots menu and current edit modal behavior must remain connected to the same record.

Very important safety rules:
- This is a live production CRM.
- Do not touch booking logic.
- Do not touch pricing.
- Do not touch payments.
- Do not touch parking.
- Do not touch website/SEO.
- Do not do broad refactor.
- Do not break the current service record creation/editing flow.
- Do not change existing service records in a destructive way.

Please inspect:
1. How service categories are currently stored:
   - JSON/array field?
   - join table?
   - text values?
   - IDs?
2. Whether existing DB schema can support per-category completion and per-category cost.
3. Whether a new child table is required, for example service_record_items.
4. Whether a JSON field would be safer or worse than a proper table.
5. Which backend service/route/schema files would need changes.
6. Which frontend components in Service.tsx would need changes.
7. How to keep existing service records backwards-compatible.
8. How Edit Service Record modal should display item completion/cost without confusing staff.
9. How expanded row should display:
   - category/item name
   - completed/pending state
   - cost per item
   - total cost
   - notes
10. How the overall service status should interact with item statuses:
   - Should completing all items automatically suggest Completed?
   - Or should overall status remain manually controlled?
   - Recommend the safest option.
