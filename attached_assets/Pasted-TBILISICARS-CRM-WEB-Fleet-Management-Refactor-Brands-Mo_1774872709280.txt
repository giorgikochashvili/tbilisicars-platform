TBILISICARS CRM&WEB — Fleet Management Refactor (Brands / Models / Vehicles)

You are working inside an existing production-style monorepo project for Tbilisicars CRM&WEB. Do NOT redesign unrelated modules. Do NOT break existing APIs, website booking flow, or CRM authentication/session logic. Apply only the changes described below, carefully and completely.

This is not a greenfield implementation. This is a targeted refactor of the existing Fleet Management module and its connected business logic.

==================================================
OBJECTIVE
==================================================

Refactor the Fleet Management area so that:
1. Brand management becomes cleaner and logo-driven.
2. Model listings become brand-aware and visually stronger.
3. Vehicle listings become correctly ordered and enriched.
4. Form inputs behave properly for manual entry.
5. Regional fleet logic supports cross-region visibility with “On Request” behavior on the website.
6. Existing project structure and logic remain stable.

==================================================
IMPORTANT BUSINESS CONTEXT
==================================================

This CRM belongs to Tbilisicars and the project already supports 3 main regions:
- Tbilisi
- Kutaisi
- Batumi

Important business rule:
- Brands are global and visible across all regions on the website.
- Specific physical vehicles belong to a region/location.
- If a model exists in the fleet globally, it should still be visible on all 3 website regions.
- If that model has no actual physical vehicle in a selected region, it must appear as “On Request” for that region instead of disappearing.

Example:
- Ford Mustang exists only in Tbilisi vehicles.
- On website search results, Ford Mustang must still appear in Tbilisi, Kutaisi, and Batumi.
- In Tbilisi it behaves as available/normal if units exist there.
- In Kutaisi and Batumi it must still be shown but with an “On Request” indicator.

This logic must integrate with the existing public website fleet/booking logic and must not break the current availability flow.

PART 1 — BRANDS TAB / BRAND ENTITY REFACTOR
==================================================

Current issue:
The Add Brand modal contains unnecessary fields and the brand system is too weak visually.

Required changes:

1. Brand create/edit fields must be reduced to ONLY:
- Brand Name (required)
- Logo Upload (optional but supported; image upload, PNG preferred)

2. Remove “Country of Origin” completely:
- Remove it from Brand create form
- Remove it from Brand edit form
- Remove it from brand validation schema
- Remove it from brand DTOs/types if present
- Remove it from fleet management displays
- Remove any dependency on it in vehicles/fleet UI

3. Brand logo behavior:
- Support uploading a car brand logo image
- PNG format should be supported
- Store the uploaded file properly using the project’s existing file/image handling pattern if one already exists
- If there is no existing upload pattern, implement a minimal safe upload/storage solution consistent with this codebase
- Show the logo in UI at a small text-height size, aligned nicely beside brand text
- Logo should later be reusable in Models and Vehicles UI

4. Duplicate prevention:
- Same brand name must not be creatable twice
- Enforce uniqueness case-insensitively and trim whitespace
- Example: “Toyota”, “ toyota ”, and “TOYOTA” must be treated as duplicates
- Show a clean validation message in UI and protect it on backend too

5. Brand edit modal behavior:
- Clicking edit on a brand must open the same modal structure used for creation, but prefilled with saved data
- It must show:
  - existing brand name
  - existing uploaded logo preview if present
- During edit, user must be able to:
  - remove the current logo
  - replace it with a new one
  - keep it unchanged

6. Brand listing/count:
- In the Brands tab/list, each brand must show how many physical vehicles belong to that brand
- This count must come from actual Vehicles data, not from model count
- Example: if Toyota has 15 uploaded physical vehicles, show 15
- The count must be accurate and derived from vehicle records through model → brand relationship

PART 4 — BRAND / MODEL / VEHICLE DATA RELATIONSHIP RULES
==================================================

Enforce and preserve these relationships:

1. Brand
- has name

- unique by normalized name

2. Model
- belongs to one brand
- has model name
- has category
- has transmission

- has status
- has year
- has color
- has mileage
