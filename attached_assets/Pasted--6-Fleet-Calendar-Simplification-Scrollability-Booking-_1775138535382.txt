#6 - Fleet Calendar Simplification, Scrollability & Booking Visibility Upgrade

We are continuing the existing Tbilisicars CRM & WEB monorepo project that is already fully built inside Replit.

Locked project state:
- Existing live project
- Replit Preview works
- GitHub sync works
- Droplet build/deploy works
- Stack: PNPM monorepo
- Do NOT touch infrastructure
- Do NOT touch deployment flow
- Do NOT do broad refactors
- Continue exactly from the current codebase state

Task:
Refine the CRM Fleet Calendar so it becomes operationally useful, scrollable, easier to read, and capable of clearly showing both past and future bookings for each vehicle.

==================================================
CURRENT PROBLEMS
==================================================

1. Fleet Calendar is too large and visually heavy
2. Too many vehicles are shown at once without enough control
3. It is not easy to review bookings around the selected time period
4. Past bookings are not visible in a useful way
5. Future bookings need to remain clearly visible
6. The calendar needs better horizontal and vertical scrolling behavior
7. The timeline should feel more like an operational planning tool, not just a giant static grid

==================================================
GOAL
==================================================

Keep the Fleet Calendar feature, but make it cleaner and more usable.

Required outcomes:
- the calendar must support horizontal scrolling through time
- the calendar must support vertical scrolling through vehicles
- staff must be able to review both previous bookings and upcoming bookings on specific vehicles
- the layout must remain understandable and performant
- the current CRM design language must remain intact

==================================================
REQUIRED IMPROVEMENTS
==================================================

A. SCROLLABLE TIMELINE
- Make the timeline area properly scrollable horizontally for date navigation
- Make the vehicle list/timeline body scrollable vertically
- Keep the layout stable while scrolling
- Avoid broken overflow or cut-off rows
- Scrolling should feel intentional and usable, not accidental

B. BETTER DATE RANGE USABILITY
- Keep the existing date range control concept if already implemented
- Improve the calendar so users can move through time more naturally
- Current range should not feel locked to only one fixed window
- Staff must be able to inspect:
  - recent past bookings
  - current bookings
  - upcoming bookings

C. PAST + FUTURE BOOKING VISIBILITY
- The calendar data/query must include bookings that overlap the visible date window, including:
  - bookings that started before the visible range but continue into it
  - bookings fully inside the visible range
  - bookings that start inside the visible range and end after it
- Also ensure the user can navigate backward to inspect recent completed/planned history and forward for future allocations
- Do NOT show only one narrow slice that hides relevant surrounding bookings

D. CLEANER VEHICLE PRESENTATION
- Keep each vehicle row compact and readable
- Preserve key info:
  - vehicle / plate
  - current availability/status
  - region/location where relevant
- Avoid oversized left panels that waste space
- Make the grid easier to scan visually

E. FREEZE / STICKY BEHAVIOR IF POSSIBLE
- Prefer keeping the vehicle identity column visible while horizontally scrolling the date timeline
- Prefer keeping the date header visible while vertically scrolling
- Only do this if it can be done safely with the current structure
- Do NOT rewrite the whole calendar from scratch unless truly necessary

F. PERFORMANCE / SAFETY
- Do not render unnecessarily heavy DOM if current implementation can be improved safely
- Keep the smallest safe change set
- Do not break current filters:
  - region
  - date range
  - status colors
- Keep existing booking color logic unless a tiny readability improvement is needed

==================================================
IMPORTANT BUSINESS RULE
==================================================

This calendar is for operations.
It must help staff quickly understand:
- which vehicle had a booking before
- which vehicle is booked now
- which vehicle will be booked next

So the calendar must clearly support operational planning across time, not only a single static view.

==================================================
STRICT SAFETY RULES
==================================================

1. First audit ONLY the current Fleet Calendar implementation
2. Identify the exact component(s), query/service(s), and scroll containers involved
3. Make the smallest safe change set
4. Do NOT touch unrelated CRM modules
5. Do NOT touch website
6. Do NOT touch infrastructure, auth, deployment, or unrelated APIs
7. Preserve current visual style as much as possible
8. Do NOT replace the entire calendar with a totally new system unless absolutely required
9. Prefer refining the existing calendar structure over rewriting from zero
10. No speculative refactors

==================================================
PLAN REQUIREMENTS
==================================================

In the plan, explicitly answer:
1. Which file renders the Fleet Calendar UI?
2. Which API/service provides the booking timeline data?
3. How the visible date range is currently calculated
4. Why past/future bookings are currently not sufficiently visible
5. What exact scroll/layout changes will be made
6. Whether sticky left column + sticky top header can be added safely
7. Whether any backend query adjustment is needed for overlapping bookings
