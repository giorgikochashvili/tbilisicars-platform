# Bookings CRM — New Booking Flow, Payment Status Logic, List Priority, and Booking Detail Navigation

What & Why

We are continuing a large existing Tbilisicars CRM&WEB project. The Bookings module is already built and working. Do not redesign or refactor broadly. Apply only the exact changes below.

This task is about improving the CRM Bookings UX and aligning the form with correct business logic:

1. New Booking should start from New Customer by default
2. Existing Customer search should be simplified into one search-driven selection flow
3. Booking status (Pending / Confirmed) must be removed from the Pricing & Notes section because it is not a pricing field
4. Payment-related status must be added and wired into the actual booking/payment logic
5. Bookings list must visually prioritize vehicle info over customer name in the Customer & Vehicle column
6. Booking detail page must have an Edit Booking action
7. Booking detail vehicle info must link to that exact vehicle’s CRM detail page

Important:
This is a production-grade CRM that is already assembled. Do not make speculative changes. Do not change unrelated layouts, APIs, schemas, workflows, routes, naming, theme, or existing working modules. Only implement the scope below.

## 4) Add Payment Status to booking form and connect it to real logic

Required new payment status options:
- Paid
- PrePaid
- Unpaid
- PreHalf

This is NOT just a visual field.
It must be connected to actual booking/payment logic so the selected payment state is meaningful in the system.

Requirements:
- Add a payment status field in the pricing/payment-related section of the booking form
- Preserve total amount and currency fields
- Notes stays as is
- Payment status must be saved with the booking in a way that existing bookings list / payment summary / payment indicators can use consistently
- Ensure current payment badges/filters/list logic continue to work or are updated consistently
- If the system already has payment-state storage, reuse and normalize it instead of duplicating fields
- If mapping is needed, do it carefully and explicitly

Business meaning:
- Paid = fully paid
- PrePaid = prepaid/advance paid
- Unpaid = nothing paid yet
- PreHalf = partially paid, specifically half-prepaid style state

Important:
Do not fabricate accounting entries or fake payment history rows unless the current system already does this by design.
If booking creation is not supposed to auto-create payment history entries, then do not auto-create them.
But the selected payment status must still be stored and reflected consistently in booking-level payment state logic.

Need to preserve:
- payment summary/history UI
- payment filters on bookings list
- payment badges if already present
- existing calculations wherever they depend on booking payment state

Done looks like:
- New booking and edit booking both support payment status
- Payment status is visible and consistent across list/detail/filter logic
- No contradictory states between booking form and booking list
