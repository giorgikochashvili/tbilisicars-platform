#16 - Tasks Filter Fix + Progress Bar Upgrade

What & Why
Two focused fixes are needed in the CRM Tasks module.

1) Assignee filter bug
Right now the Tasks page reads `?assignee=me` from `window.location.search` inside an effect that depends on `user`. That means it only reacts when `user` changes. If the user opens `/tasks?assignee=me` from the Dashboard widget and then later navigates back to `/tasks` from the sidebar, the Tasks page component can stay mounted, `user` does not change, and the effect does not run again. Result: the assignee filter remains stuck on the current user, so other team members’ tasks disappear until manually reset.

2) Progress bar styling
The current shadcn `<Progress>` bar looks flat and weak in the dark CRM UI. Replace it with a small custom inline progress bar component that feels premium, has better contrast, and communicates progress state with refined color changes.

Done looks like
- Opening `/crm/tasks` from the sidebar always shows all tasks
- The assignee filter visibly shows `All assignees` on `/crm/tasks`
- Opening `/crm/tasks?assignee=me` from the Dashboard widget correctly filters to the current user
- Navigating from Dashboard “My Tasks” widget back to Tasks via the sidebar resets the filter back to `All assignees`
- Refreshing the page always respects the current URL state
- Progress bars in both the task table and task detail drawer use the new premium custom bar
- Progress colors change meaningfully:
  - 0% = muted/dark
  - 1–39% = warm low-progress tone
  - 40–79% = active mid-progress tone
  - 80–99% = high-progress positive tone
  - 100% = completed/success tone
- No regression in task creation, filtering, task counts, or Dashboard widget behavior

Out of scope
- Backend task logic
- Task ownership logic
- Task creation flow
- Dashboard widget navigation changes
- Any other CRM pages/components

Required changes

1. Make assignee filter fully URL-driven and reactive
- In `artifacts/crm/src/pages/Tasks.tsx`, stop using `window.location.search` for this behavior.
- Use Wouter’s reactive search hook instead, specifically `useSearch()`.
- Parse the query string from `useSearch()` and keep the assignee filter synchronized with the URL.
- Logic:
  - if query contains `assignee=me` and current user exists, set filter `assigneeId = user.id`
  - if query does NOT contain `assignee=me`, reset filter `assigneeId = "all"`
- This must react whenever the URL query string changes, even if the Tasks component stays mounted.
- This must also still work correctly on first load and after refresh.
- Do not break any existing filters, counts, or query behavior.

2. Replace current Progress component usage with custom TaskProgressBar
- Build a small reusable inline component inside `artifacts/crm/src/pages/Tasks.tsx` named something like `TaskProgressBar`.
- Do NOT use shadcn `<Progress>` for task progress anymore.
- Use simple div-based markup for track + fill + numeric label.
- The bar should fit the dark CRM theme and look more polished than the current one:
  - rounded track
  - subtle premium dark track background
  - smooth fill
  - slightly glowing / richer fill appearance but still elegant
  - no harsh neon colors
- Use percent-based styling logic:
  - 0%: muted charcoal / slate style
  - 1–39%: warm amber tone
  - 40–79%: blue tone
  - 80–99%: emerald tone
  - 100%: success green tone
- Clamp values safely between 0 and 100.
- Keep the numeric percent label visible and readable.

3. Replace all task progress render points
- Use the new custom component in:
  - the task table progress column
  - the task detail drawer progress section
- Remove old task-specific `<Progress>` usage in those spots.
- Keep spacing/alignment clean in both compact and detailed contexts.

4. Keep Dashboard behavior unchanged
- Do not change Dashboard links/navigation logic.
- `/tasks?assignee=me` from Dashboard must continue to work.
- Only fix Tasks page behavior so URL state always wins.
