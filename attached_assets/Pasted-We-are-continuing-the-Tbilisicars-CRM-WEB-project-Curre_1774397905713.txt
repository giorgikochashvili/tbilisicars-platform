We are continuing the Tbilisicars CRM&WEB project.

Current completed foundation:
Phase 1 is done.
A read-only admin AI data layer already exists and works under these admin-only endpoints:

- GET /api/admin-ai/summary
- GET /api/admin-ai/bookings
- GET /api/admin-ai/bookings/:id
- GET /api/admin-ai/vehicles
- GET /api/admin-ai/customers
- GET /api/admin-ai/logs

These endpoints are protected by admin auth and already provide structured operational data, audit trail, diagnostics, and anomaly explanations.

Now implement:

PHASE 2 — SUPER ADMIN AI BRAIN
This phase is NOT autonomous action mode.
This phase is READ + REASON + EXPLAIN only.

Main goal:
Create an internal admin-only AI assistant inside the CRM that can answer operational questions by using the existing /api/admin-ai/* endpoints and returning clear, grounded, explainable answers.

Critical project intent:
This AI is for Tbilisicars internal super admin use.
It should behave like an operations analyst + admin assistant.
It must help understand what is happening in the system.
It must NOT invent facts.
It must NOT pretend to know things it did not retrieve.
It must explain uncertainty when data is incomplete.
It must be grounded in real CRM data.

DO NOT:
- Do not add write actions yet
- Do not create/update/delete bookings, vehicles, customers, payments, parking, services, etc.
- Do not build autonomous workflows yet
- Do not make the AI directly call database queries bypassing the existing admin-ai layer
- Do not break or refactor existing CRM modules unnecessarily
- Do not rebuild the app shell

Build a safe first version of an admin-only AI assistant with these parts:

1) Backend AI chat endpoint
Create a new admin-only endpoint, for example:
POST /api/admin-ai/chat

Protected by existing requireAdmin middleware.

Request body:
{
  "message": "..."
}

Response shape should be structured and consistent, for example:
{
  "answer": "...",
  "usedSources": [
    { "type": "summary" },
    { "type": "bookings", "count": 6 },
    { "type": "logs", "count": 12 }
  ],
  "reasoningMode": "grounded-readonly",
  "warnings": []
}

2) Server-side orchestration layer
Create a backend orchestration/service layer that:
- receives the admin question
- determines which existing /api/admin-ai/* data source(s) are needed
- fetches the relevant internal data
- builds a safe structured context
- sends that context to the AI model
- returns a clean final answer

Very important:
Do not let the model hallucinate broad system knowledge.
Always retrieve real data first.
The orchestration layer should decide which of these sources to use:
- summary
- bookings
- booking details
- vehicles
- customers
- logs

Examples:
- “What happened today?” → use summary + logs
- “Why was booking TC-000006 not completed?” → use booking details + logs
- “Which cars are free?” → use vehicles + maybe summary
- “Which bookings have unpaid balance?” → use bookings
- “Why is this car not in parking?” → use vehicles + logs + diagnostics if relevant

3) Intent routing / tool selection
Implement simple deterministic intent routing first.
Do NOT overbuild with complex agent loops.
Use keyword + rule-based routing to choose which internal sources to read.

Suggested initial intents:
- summary_overview
- booking_lookup
- unpaid_bookings
- available_vehicles
- customer_lookup
- diagnostics_lookup
- today_activity
- unknown_general

For unknown_general:
use summary + logs first, and optionally bookings/vehicles if helpful.

4) Grounded answer generation
Use the AI model only after real data has been retrieved.
The prompt to the model should instruct it:
- answer only from provided data
- do not invent missing details
- if the answer is incomplete, say what is missing
- explain operational reasons clearly
- be concise but useful
- prefer admin-friendly explanations over technical jargon
- if a failure reason exists in diagnostics/logs, surface it clearly

5) Admin-only CRM UI
Add a small admin-only page or panel in CRM for the Super Admin AI.
Keep it simple and safe.
Do not overdesign.

Requirements:
- accessible only to logged-in admins
- simple chat layout
- one input box
- send button
- scrollable conversation area
- show assistant replies clearly
- show optional “used sources” under each answer
- loading state
- graceful error state
- dark CRM style consistent with existing UI

Suggested placement:
- new sidebar item: “Admin AI” or “Super Admin AI”
- route like /crm/admin-ai

Keep the UI minimal and production-clean.
This is an internal tool, not a public chatbot.

6) Safety / trust behavior
This is mandatory.

The assistant must:
- explicitly stay read-only in this phase
- never claim an action was performed
- never say a booking was changed, created, canceled, or assigned
- never promise future actions
- never fabricate database state
- clearly say when parking/module data is unavailable
- clearly mention when a booking has no assigned vehicle if diagnostics show that
- clearly distinguish between facts from logs vs current inferred anomalies

7) Response style
The AI should answer in a helpful internal-ops tone.
Prefer direct, operational wording such as:
- “Booking TC-000006 is confirmed but currently has no assigned vehicle.”
- “I found 2 available vehicles.”
- “There are 3 canceled bookings and 1 confirmed booking.”
- “I do not see a completed pickup today.”
- “I could not confirm parking information because parking data is unavailable in this environment.”

Avoid vague marketing language.
Avoid sounding like a generic chatbot.

8) Configuration
Use the project’s existing environment/config pattern.
If OpenAI integration is not already set up, add it safely via environment variable such as OPENAI_API_KEY.
Use a clean service abstraction so the model provider can be swapped later if needed.

Important:
Do not hardcode secrets.
Do not expose API keys to frontend.
All model calls must happen server-side.

9) Logging / observability
Add lightweight server-side logging for AI requests:
- question received
- chosen intent
- sources used
- success/failure
But do not log secrets or excessive sensitive content.

10) Constraints for this phase
This phase must remain READ-ONLY.
No mutations.
No action execution.
No workflow automation.
No database writes except optional safe internal request logging if the project already has a pattern for that.
If such logging complicates things, skip DB logging and keep normal server logs only.

11) Expected capabilities after this phase
The super admin should be able to ask questions like:
- What happened today?
- Which bookings are unpaid?
- Which cars are currently available?
- Why is booking TC-000006 problematic?
- Show me the situation in fleet right now.
- Do we have overdue returns?
- Which customer has recent bookings?
- Why might parking info be missing?
And get answers grounded in real CRM data.

12) Implementation guidance
Follow existing project patterns for:
- routes
- services
- validation
- auth
- frontend routing/layout
- TypeScript typing

Prefer small focused files.
Do not introduce unnecessary framework changes.
Do not break existing pages.

13) End-of-task output
At the end provide:
- exact files created/updated
- endpoint contract for POST /api/admin-ai/chat
- intent routing summary
- AI prompt / grounding strategy summary
- UI route/path
- environment variables required
- safe testing checklist
- known limitations for this read-only phase
- recommended next phase for controlled action mode

Critical business rule:
This phase is about making the AI useful and trustworthy before giving it permissions.
The user is non-technical, so the result must be stable, understandable, and easy to test.
Do not overbuild. Build a clean, grounded, read-only Super Admin AI Brain.
